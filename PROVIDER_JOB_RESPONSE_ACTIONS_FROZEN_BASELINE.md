# iFixIt — Provider Job Response Actions Frozen Baseline

**Status:** FROZEN / APPROVED BASELINE  
**Date:** 2026-08-20  
**Scope:** Provider response actions, provider offer-attempt records, and the approved system-generated no-response outcome.

## 1. Approved Provider Response Actions

```text
ACCEPT
DECLINE
REQUEST_CLARIFICATION
```

These are the only provider-selected actions at the initial offer/assignment response stage.

## 2. Approved System-Generated Outcome

```text
NO_RESPONSE_TIMEOUT
```

`NO_RESPONSE_TIMEOUT` is not a provider-selected action. It is generated by the system when the provider takes none of the approved actions before the configured response deadline expires.

## 3. Frozen Table

```text
provider_job_offers

offer_id
service_request_id
provider_id

offered_at
response_deadline_at
responded_at

response_status
decline_reason

expired_at

created_at
updated_at
```

### Purpose

`provider_job_offers` stores each provider offer attempt for a single customer service request. A service request may therefore have multiple historical provider offer attempts without creating duplicate service requests.

## 4. Field Logic

- `offer_id` — unique identifier for the provider offer attempt.
- `service_request_id` — references the existing customer service request.
- `provider_id` — identifies the provider receiving this offer attempt.
- `offered_at` — timestamp when the offer was presented to the provider.
- `response_deadline_at` — deadline for the provider to respond.
- `responded_at` — timestamp when the provider selects an approved response action; NULL when no response was given.
- `response_status` — stores the provider response or system-generated timeout outcome.
- `decline_reason` — optional reason when the provider declines; otherwise normally NULL.
- `expired_at` — timestamp when an unanswered offer expires and transitions to `NO_RESPONSE_TIMEOUT`.
- `created_at`, `updated_at` — record audit timestamps.

## 5. Response Status Logic

Approved values at this stage:

```text
PENDING
ACCEPT
DECLINE
REQUEST_CLARIFICATION
NO_RESPONSE_TIMEOUT
```

`PENDING` represents an active offer awaiting provider action.

## 6. Response Meanings

### ACCEPT
The provider agrees to take responsibility for the offered job, subject to downstream scheduling, staffing, pricing, and execution workflow.

### DECLINE
The provider refuses the offered job. `decline_reason` may be recorded for audit and matching-quality analysis.

### REQUEST_CLARIFICATION
The provider requests additional information before deciding whether to accept or decline. This is not equivalent to acceptance.

### NO_RESPONSE_TIMEOUT
The provider does not submit `ACCEPT`, `DECLINE`, or `REQUEST_CLARIFICATION` before `response_deadline_at`. The system closes that offer attempt as timed out/no response.

## 7. Frozen Business Rules

1. `ACCEPT`, `DECLINE`, and `REQUEST_CLARIFICATION` are provider-selected actions.
2. `NO_RESPONSE_TIMEOUT` is system generated and must not be manually selectable by the provider.
3. Every provider offer attempt belongs to exactly one `service_request_id` and one `provider_id`.
4. One service request may have multiple `provider_job_offers` records over time.
5. Provider offer attempts must never create duplicate customer service requests.
6. A new offer begins with `response_status = PENDING`.
7. If the provider responds, `responded_at` must be recorded.
8. If the provider declines, `response_status = DECLINE`; `decline_reason` may be populated.
9. If the provider accepts, `response_status = ACCEPT` and downstream job execution may begin.
10. `REQUEST_CLARIFICATION` does not equal acceptance and must not automatically mark the job as accepted.
11. If the response deadline expires with no provider action, the system sets `response_status = NO_RESPONSE_TIMEOUT` and records `expired_at`.
12. `NO_RESPONSE_TIMEOUT` closes only the current provider offer attempt; it does not automatically cancel the customer service request.
13. All responses and timeout transitions must be timestamped and audit logged.
14. Historical provider offer attempts must be retained for provider-response metrics, matching analysis, and dispute/audit purposes.

## 8. Relationship

```text
SERVICE_REQUEST
1 → many PROVIDER_JOB_OFFERS

PROVIDER
1 → many PROVIDER_JOB_OFFERS
```

Example:

```text
Service Request #1452
├── Provider A → NO_RESPONSE_TIMEOUT
├── Provider B → DECLINE
└── Provider C → ACCEPT
```

The service request remains `#1452` throughout.

## 9. Frozen Principle

Provider response handling is modeled as historical offer attempts. A provider may choose `ACCEPT`, `DECLINE`, or `REQUEST_CLARIFICATION`; if no action is taken before the configured deadline, the system records `NO_RESPONSE_TIMEOUT`. Each attempt is retained without duplicating or replacing the underlying customer service request.
